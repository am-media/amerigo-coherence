# Convergence

**First read `../../CONSTITUTION.md`.** Apply its universal principles to technology, design, data, interfaces and architecture. Before a nontrivial technology or abstraction choice, compare the simplest plausible adequate alternative and state why it fails if rejecting it. A merely plausible benefit does not establish necessity.

1. Restate the desired user outcome and any deadline without presuming a technology. If timeboxed, inspect the existing state and select a complete outcome compatible with the timebox; explain necessary trade-offs and estimate uncertainty without speculative padding. Consider a spreadsheet, existing tool, or no code.
2. If a repository is bloated, stalled, or already in progress, choose `retrofit-existing-repo`. Declare exactly one mission: PROVE_CORE, SHIP_MVP, or ADD_FEATURE. Establish a recoverable baseline, then classify active components CORE / REQUIRED / DEFER / REMOVE. Prioritize disconnecting speculative nonessential code from the active runtime, with explicit approval for the bounded isolation task and verified rollback. Otherwise choose exactly one recipe from `../../recipes/` and record why. Read only that recipe.
3. For retrofit work, run optional `../../tools/retrofit.py` on the target Git repo and review its report as hypotheses, not verdicts. Do not mistake an inventory signal for proof. Trace real runtime dependencies. Remove nonessential items from the active execution path (not just from the prompt), keeping Git history or archive branch for recovery. No destructive data operations or blanket rewrites. Before coding, specify the outcome, acceptance evidence, allowed file paths, exclusions, and stopping condition. Small tasks can use a short inline contract. For substantive code changes use `../../templates/task.json` and keep it outside the agent's editable paths; the YAML template remains a human planning example.
4. BEFORE EACH EDIT: locate then read the full relevant source file (chunked if large), including its imports, exports and side effects; inspect callers and dependencies. Search/grep finds candidates, not understanding. Identify existing tests and their coverage; for new meaningful behavior add a focused executable test documenting the protected contract and the regression it catches (a simple mocked producer/consumer boundary is enough). For generated/very large files inspect hand-written authoritative source and disclose limits. THEN implement one small working vertical slice. Prefer the existing stack and TDD for suitable behavior. Do not rewrite unrelated files. **No framework by default:** build bounded independent modules and the smallest explicit connections; do not introduce generic abstraction infrastructure for future scenarios. A simple adapter file is sufficient where appropriate.
5. Before creating a domain/entity/function/contract, ask whether existing owner data or a typed parameter expresses the requirement. Prefer extending the existing cohesive owner to creating a domain per noun. A database ID is not proof of independent domain identity. Separate only for demonstrated independent lifecycle or responsibilities.
6. If the project is Git-backed and the JSON contract applies, run `python tools/guard.py .coherence/task.json --base origin/main` from the target repository (adapt the guard location and trusted base). Treat a failed guard as a blocked task, not permission to widen the contract.
7. Run the requested behavior, affected consumers, and relevant regression checks after editing; classify red tests as REPAIR / UPDATE / RETIRE based on whether their requirement remains valid; repair active contracts, update explicitly changed ones, retire only intentionally removed behavior, and rerun surviving regressions before completion. Run actual acceptance and regression checks separately: passing the scope guard proves **only scope compliance**.
8. After two unsuccessful attempts against the same criterion, trigger a strategy review; do not continue cycling blindly.
9. Report one of four outcomes: ADOPT (verified, stop), FIX (bounded work), PIVOT (requires strategic decision), ABANDON (stop with reasons). See `../../docs/decisions.md`. Never claim verification without evidence.

This skill cannot prevent all agent deviations. Use independently configured CI, permissions and protected branches for essential controls. Do not allow an agent to approve its own expansion of scope.
